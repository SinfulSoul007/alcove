# Profiles implementation plan

> Execute inline using executing-plans. Existing user authorization covers continuous building, commits and pushes in this checkout. Keep the full acceptance ledger active.

**Goal:** Add real profile-owned website storage and library state with safe migration/lifecycle and native management.
**Architecture:** Codable registry and per-profile libraries inside encrypted metadata; existing Spaces use WebKit default, new profiles use named stores; private stays ephemeral. Persist transitions before applying them.
**Spec:** docs/superpowers/specs/2026-11-07-profiles-design.md

## Global Constraints
- macOS 14+, AppKit/SwiftUI/WebKit; no external packages, analytics or accounts.
- Preserve existing tabs/logins/bookmarks/history; never map one named profile to another's cookie store.
- No normal metadata/key/store access from private mode. Never transfer cookies between profiles.
- Native 0.4 visual QA remains pending app access. This increment cannot complete full Arc parity alone.

## Review Focus
- A background opener/profile changes while its popup or navigation callbacks arrive: retain the originating profile, reject stale callbacks.
- Failed encryption save while creating/assigning/deleting: preserve live state and recoverable registry, with no accidental cookie-store recreation.
- Old or malformed registries with orphan/duplicate/zero IDs: keep data and prevent cross-profile fallback.
- Profile changes during an asynchronous deletion: prevent attaching to a pending store; confirm final persistence and retry.
- Website-data clearing or archives spanning multiple profiles: affect the selected/owning profile only.
