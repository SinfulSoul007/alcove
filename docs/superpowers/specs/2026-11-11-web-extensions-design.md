# WebKit extension hosting

Build working extension installation, permissions and browser integration toward the full Arc-like browser goal. This increment does not complete the browser or establish universal Chrome-extension compatibility. The user has delegated implementation choices and authorized the existing main-checkout, commit/push, native testing and unsigned-preview workflow; no repeated design or execution-mode gate.

## Approach

Use Apple's public `WKWebExtension` engine, available on macOS15.4+, with Alcove supplying package handling, account boundaries, browser/window/tab adapters and native controls. Keep the browser's macOS14 minimum; earlier systems preserve installed metadata and show an unavailable state instead of calling unavailable APIs. A hand-written JavaScript extension API would duplicate the engine and introduce a large isolation surface. Returning to Chromium contradicts the chosen WebKit architecture.

An owned, explicitly transient runtime probe already passes five checks on macOS26.7.1: no content injection without host permission, host permission alone does not expose private data, explicit private approval permits injection, unattached views do not inherit extensions, and revocation blocks subsequent documents. This proves a feasible engine path, not an Alcove feature or third-party compatibility claim.

## Packages and persistence

Support unpacked folders, ZIP and authenticated CRX3 packages; add Chrome Web Store URL/ID installation and manual update checks. No Arc profile files, extension source or browsing data are imported. Third-party code is neither executed nor committed as a test fixture without the required specific authorization. Tests create and sign their own packages.

Copy validated packages into Alcove-owned immutable revision directories under the metadata directory. Derive paths only from profile UUID, controlled package UUID (normally the record UUID) and SHA-256 digest; never persist a caller-supplied absolute resource path. Imported resources are plaintext code/assets, not part of metadata encryption. Names, preferences, grants and installed-package references belong to encrypted per-profile libraries. WebKit owns extension runtime storage, isolated through a durable controller identifier per profile and the profile's explicit website data store.

Bound imports before allocation/extraction:128MiB input,256MiB total expanded data,64MiB per file,10,000 entries,1MiB manifest,16MiB CRX header and64 signature proofs. Accept stored/deflated ZIP entries with validated central/local headers, sizes, CRC and normalized unique names. Reject traversal, absolute/drive/backslash paths, special files, links, encrypted/multipart archives and ambiguous overlapping entries. Do not run a shell extractor on untrusted paths. Use system zlib for bounded raw-deflate decoding. Exclude source-control/Finder metadata when copying a folder; pin the selected root and do not follow nested links. Check actual descriptor sizes and cap bytes while reading, not only declared archive sizes.

CRX3 verification authenticates the signed header and complete archive, binds the developer key to its extension ID and, for Web Store downloads, requires the production publisher proof as well. Implement the current Chromium verifier's RSA PKCS#1 SHA-256 and ECDSA SHA-256 behavior rather than trusting an outdated schema comment. Local unsigned folders/ZIPs remain visibly unsigned. A valid signature establishes package identity, not that its code is safe. CRX2 and encrypted archives receive explicit unsupported-format errors.

Prepare and inspect packages without executing their scripts. A preview records source, manifest identity, requested/optional API and site access, native-engine diagnostics, code digest and the intended profile. Only a later explicit approval may publish an enabled record and load its context. Updates preserve stable record identity and old working resources until the new package validates and its permission review succeeds; changed code needs fresh approval. Failed/cancelled/stale installs preserve the existing catalog, live pages and ciphertext. Cleanup only installer-owned staging/revisions that were not published; reconcile crash orphans within the owned package root.

Metadata format5 migrates1–4 and rejects6+. Existing0.8 readers reject5 rather than discarding extension identities/grants. Each profile gains an optional durable `extensionControllerID`, assigned and saved before a persistent native controller can be created. Repair duplicate/reassigned account/controller/record identities without reusing approvals or another profile's extension storage. Clearing a profile unloads contexts, erases extension runtime data, revokes grants and leaves installed definitions disabled for deliberate re-enabling. Deleting a profile removes its installed packages/catalog/runtime data. Interrupted operations remain unavailable and retryable, using the existing durable profile-operation protocol.

## Host and private browsing

One native controller per normal profile uses that profile's explicit website data store and durable controller ID. Attach it to main, split, Favorite, Quick Browse, Peek and popup configurations before creating their WKWebViews. A per-profile preparation gate holds navigation decisions until enabled contexts finish validation/loading; tickets are bounded, complete once and cancel on newer navigation, source closure, profile operation or shutdown. Missing/tampered/failed packages produce a visible Retry/Continue Without action instead of silently bypassing expected extensions. Empty catalogs do not delay browsing. Do not weaken the metadata/Keychain startup gate.

Adapters expose actual browser windows/tabs and their account, URL, title, selection, pin, zoom and loading state; route create/update/activate/close/reload/duplicate/back-forward operations through current store transactions. Notify the engine on real lifecycle/property changes. Same-profile live handoffs keep the web view/controller/adapter identity; cross-profile handoffs retain existing reload consent and cannot carry a source controller. Extension URLs are permitted only for a loaded matching context and profile, never handed to an external application or accepted as arbitrary file access. Options pages, action popups/badges, commands and extension tab-context items use the public API. Validate source liveness and account before actions, popup presentation and every asynchronous permission reply.

Private extension access is off until explicitly allowed for an extension in its normal profile. Private website storage and user-content controllers remain separate. A private window opened from a ready normal profile can share that profile's extension controller, while adapters expose it only to permitted contexts. An auxiliary normal-owner lease keeps this controller and its approved runtime alive until associated private windows close, including after the main window closes. Private permission prompts can grant only transient session access; they do not save private URLs or new grants to normal metadata. An extension explicitly allowed in private can itself retain/transmit information; explain this at approval.

Private windows opened while normal data is locked remain immediately usable without a Keychain request or persistent controller. Once the normal profile is available, an explicit Reopen With Extensions flow can recreate their temporary session after warning that live forms will be lost. Never silently reload a private form. Revalidate revoke/remove/profile-clear operations in all associated windows. Closing private windows removes their transient grants and auxiliary leases. By default, standalone private stores still request no key and write no normal metadata.

Unsupported native messaging/companion-app or developer-tool APIs stay honestly unavailable rather than emulating privileged behavior. Their secure integration and real vendor interoperability remain unfinished parts of the full goal. Report engine/manifest/API limits before installation and in Details; do not label an extension compatible merely because its manifest parsed.

## Installation and native controls

Provide an Extensions manager from the app menu, Settings, command bar, main sidebar and Quick Browse. It has the current profile selector, install folder/ZIP/CRX, Web Store URL/ID, source/version/status, enable/disable, site/API/private access, options, updates, removal and retry controls. Use explicit actions for installation/removal/update and persist before granting privilege. Do not grant the requested set automatically on load. Keep controls scrollable/reachable in short windows and at large text; native popovers follow the source window and close on its teardown.

Web Store requests use an ephemeral session without account cookies/credentials or browsing history. Resolve the current published stable Chrome package-selection version from Google's public version service, then request a CRX3 from the official update endpoint for the validated32-letter a–p extension ID. Limit streaming bytes/time and redirect count; accept only the named HTTPS Google update/CDN origins, verify signatures/expected ID, and leave the old install untouched on failure. A download does not establish WebKit compatibility. No silent update install; new code returns to review.
