# Self-contained WebKit app packaging

## Intent and authority

The user wants a downloadable macOS browser with Arc's features, regular updates, extensive customization, polished onboarding/sidebar behavior and Chrome extensions, specifically original full uBlock Origin. This work puts the already qualified engine into a real app bundle. It does not replace the full browser objective or establish arbitrary Chrome compatibility.

The user has authorized implementation, repository pushes and downloadable releases and has asked to continue without repeated design/permission questions. The packaging choices below are engineering decisions, not preferences explicitly selected by the user.

## Approach

Use the exact verified source-built graph as input to an explicit packaging transform, retaining immutable input receipts and a separate post-transform manifest. Create an opt-in, clearly labeled Apple Silicon/macOS 26.5 development candidate and qualify it before any public engine promotion. Keep the current macOS 14+/Intel/system-WebKit build and release path intact. Wider engine portability remains required work toward the original objective.

Other approaches considered: continuing to require developer environment variables would not produce the requested downloadable app; replacing the complete engine with a smaller subset would discard the graph that passed the genuine extension witness; immediately rebuilding WebKit would spend another full build before packaging defects are known. Those alternatives do not establish this deliverable.

## Required behavior and invariants

1. Verify pinned source/artifact/member/link/framework receipts before copying anything. The source runtime remains unchanged. Preserve the complete approved graph and its resources, including sandbox profiles, locales, Swift support and framework/service bundle identities required by WebKit. Do not copy profile data, credentials or test outputs into the product.
2. Resolve all engine-owned Mach-O dependencies inside the copied bundle with a complete relative install-name/rpath map. Keep Apple system dependencies pointing to the system. Strip only developer framework/library-search load commands; do not alter executable code or data sections. Reject malformed/unsupported images and incomplete/unmapped owned dependencies before publishing output. Record exact input/output hashes and allowlisted load-command changes, and prove section bytes are unchanged.
3. The normal app entry point must load the packaged engine without `DYLD_FRAMEWORK_PATH`, `DYLD_LIBRARY_PATH`, `__XPC_DYLD_FRAMEWORK_PATH` or other developer overrides. A missing/incompatible graph fails visibly rather than silently advertising full extension support on system WebKit. Actual `Bundle(for: WKWebView)` must resolve to the candidate's verified embedded framework.
4. Sign nested executable components and containers in dependency order, then the app, using Hardened Runtime and explicit per-role public entitlements. Preserve the app's existing six entitlements. Do not add `get-task-allow`, disable library validation, disable the sandbox, copy Apple-private entitlement policy or disable platform protections. JIT requirements belong only to the WebContent role where technically necessary and must have direct native evidence. Any unproven helper entitlement remains a qualification gate rather than an invented shipping promise.
5. Preserve WebKit's sandbox-resource and XPC/service lookup behavior; do not blindly rename `com.apple.WebKit` framework/service identifiers or replace service confinement. No debugger, interposition, process tracing or injected libraries are part of the package.
6. Retain the exact frozen full-uBlock witness SHA-256 `2155d8b27904ca8105f3debee0d3f30242fa387c13d39d0072ed3fcdfea7b725` and original vendor assets/hashes in the native qualification. Test-only ownership journals must use the qualification app's writable sandbox storage, not its own executable directory. This must not touch real Alcove profiles/Keychain. Do not relax readiness, filtering, code-integrity or cleanup assertions.
7. Run the witness in an actually sandboxed/Hardened Runtime self-contained app, with the launcher environment cleared, and verify the real engine root plus its post-transform manifest. Repeat exact ZIP/CRX dashboard, request-count, cosmetic, disable/re-enable and cleanup assertions. Separately build and launch the actual ordinary app entry point with the same packaged graph. A harness alone does not prove the ordinary app or installed/downloaded package.
8. Include engine source/license notices, exact source/patch/build references and corresponding source availability with the candidate. The app remains independently written. No Arc assets/source or proprietary downloaded engine binaries enter the repository.
9. Compatibility messaging must describe the engine actually loaded. The proven normal-profile witness does not enable private-extension support or certify every vendor/API. Current private-DNR version parsing and full-uBlock manager copy require deliberate follow-up. Preserve reviewed permissions and visible failure recovery.
10. Do not change public tags, updater compatibility targets or public supported-platform claims until app/native/package gates establish the corresponding result. Maintain separate input-engine, transformed-engine, test-app, ordinary-app, downloadable-package and public-update evidence.

## Deliverable and remaining scope

This plan must produce a reproducible packaging command, rejection/derivation checks, a complete candidate app and actual native evidence. Failed native packaging is a concrete defect to diagnose; it does not justify calling the browser complete or substituting uBlock Lite. macOS 14+/Intel portability, broad Chrome compatibility, private-extension behavior, actual installation/update transitions, website fullscreen/PiP, visual/accessibility/performance/site/security checks and the rest of the Arc acceptance ledger remain part of the active goal.
