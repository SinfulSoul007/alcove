# Extension package verification

Alcove inspects packages before granting permissions or loading a native extension context. Folder/ZIP sources stay unsigned. Imported code/assets are plaintext files; catalogs and grants use the existing encrypted metadata file. A signature establishes identity, without certifying code safety or engine compatibility.

CRX3 authenticates its exact signed-header bytes and ZIP payload. Every supplied RSA or P-256 proof must verify, and a developer key must match the signed 16-byte ID. RSA uses PKCS#1 v1.5 with SHA-256, following the [pinned Chromium verifier](https://raw.githubusercontent.com/chromium/chromium/3b505743bc9f8871e748b0dc79fff94d5a3c2416/components/crx_file/crx_verifier.cc); its schema's PSS comment does not describe current verifier behavior. Web Store downloads additionally require the production publisher SPKI SHA-256 `61f7f2a6bfcf74cd0bc1fe2497cc9b04254c658f79f2145392867ea8366367cf`. Test publisher keys are never accepted. The [schema](https://chromium.googlesource.com/chromium/src/+/HEAD/components/crx_file/crx3.proto) describes framing; strict DER/protobuf bounds reject ambiguous encodings. Alcove's RSA range is2048–8192 bits.

ZIP parsing checks central/local records, descriptors, CRCs, names, ranges and resource caps before publication; it accepts stored/raw-deflated resources. See [PKWARE's format](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT) and [zlib](https://zlib.net/manual.html). Filesystem operations pin directory/file descriptors, reject links and copy a bounded snapshot. Immutable revision names derive from account/package UUIDs and a deterministic resource digest. Exclusive publication preserves an existing revision, and cleanup stays bound to installer-owned directories.

The development checks use owned ephemeral keys and resources. Positive production-publisher verification and actual engine/vendor interoperability remain separate gates. This foundation is not yet exposed by the public0.8 browser.
