# System WebKit request-blocking compatibility

The browser still supports macOS 14, and native extension hosting remains guarded at macOS 15.4. A separate engine capability boundary applies to request-blocking extensions in private sessions.

An owned rule blocked a real loopback fetch on system WebKit `21624.5.1.11.3`, but the same rule did not block on `20621.3.11.11.3`. The working control returned HTTP 200 and registered content scripts ran. Registered/visible windows, application bundles, typed/untyped rules and Xcode 16.4/26.3 did not resolve the older-engine failure. An independent public `WKContentRuleList` worked, isolating the extension path.

WebKit's [301720 fix](https://bugs.webkit.org/show_bug.cgi?id=301720) adds existing request rules when a new user-content controller appears. The [related Safari report](https://bugs.webkit.org/show_bug.cgi?id=303118) describes the same private/new-window symptom. The stable [623 branch](https://github.com/WebKit/WebKit/blob/safari-7623-branch/Source/WebKit/UIProcess/Extensions/Cocoa/WebExtensionControllerCocoa.mm) omits the call; the [624.1.16 branch](https://github.com/WebKit/WebKit/blob/safari-7624.1.16-branch/Source/WebKit/UIProcess/Extensions/Cocoa/WebExtensionControllerCocoa.mm) includes it. [Apple's release index](https://developer.apple.com/documentation/safari-release-notes/) identifies Safari 26.4 as build 20624.1.16. The app checks the actual loaded system framework version, rather than the separately installed Safari app or compiler SDK.

Normal profiles on affected engines reuse their own content controller. After explicit approval, a URL-less native view registers it before request rules compile; this also covers static blockers without a background page. The view is never a browser tab and is released on runtime unload. Fixed engines need no such view. The original normal blocking assertion and its unapproved-private grant remain unchanged. This passed the original network/erasure control on macOS 15, alongside the existing private-isolation suite. Content controllers are not shared across profiles or into private sessions.

For private sessions, sharing a normal content controller would violate isolation. Creating a separate inert view or loading a generated blank document did not repair the older-engine behavior. Instead, the compatibility floor is the known fixed stable branch 624.1.16. Unknown/malformed framework versions fail closed for this capability. New private blocking approvals and private association/reload are refused before replacing pages. Existing approvals remain saved; unsupported native private access is withheld. Other supported spanning extensions can still use private browsing. A future backport below this conservative floor requires verification before changing it.

Tests retain the original normal blocked/control request. Fixed engines additionally exercise two new explicitly approved private clients with distinct content controllers and real blocked/control requests. Affected engines test approval refusal, a legacy saved grant, native private-access withholding, association refusal, a once-completed reload refusal before consent, preserved form/view/ciphertext and no private key request. Private storage-erasure fixtures use only storage/scripting permissions; their original native erasure and form/cookie retention assertions remain in place and do not depend on unavailable private blocking.

This boundary does not certify full Chrome compatibility, every uBlock Origin Lite filter or Safari performance parity. Full uBlock Origin remains unsupported. Intel and minimum-OS hardware testing remain separate from compilation.
