# Extension-to-website popup compatibility gap

The development Mac (macOS 26.7.1, Apple Silicon) reproduces a blank HTTP popup when its opener was created with `WKWebExtensionContext.webViewConfiguration`. This also happens in a bare `WKUIDelegate` that returns a new `WKWebView` using the exact supplied configuration, without Alcove's navigation or model code. The equivalent ordinary HTTP opener loads its HTTP child successfully. A popup targeting the same extension origin also loads and retains that extension's account storage.

The controlled fixtures use generated extension resources and a loopback website. Only the hidden owned opener enables automatic popups at construction so that WebKit actually delivers its callback. Production extension documents keep the ordinary automatic-popup restriction. The failing HTTP child received an allow decision and the correct owning controller and website store; mounting it did not resolve the blank page.

Alcove currently refuses this extension-to-website popup before publishing a tab, returns failure to the opener, and displays an explanation. A related extension popup cannot be silently replaced with an unrelated website view: that would discard its native opener relationship. Its existing document and form remain intact when such a navigation is refused. Normal extension tabs and Peeks can separately transition to ordinary website configurations, and the extension tabs API can create a regular website tab.

**This capability remains unfinished.** The current refusal is an explicit compatibility boundary, not implementation of `window.open`/`window.opener` interoperability. The reproduction does not establish that every possible public-API solution is impossible. Revisit the boundary when a documented approach preserves both the supplied popup configuration and actual opener/message behavior, with generated end-to-end coverage. Do not strip private WebKit configuration fields, use KVC/SPI, emulate browser APIs, or label a third-party extension compatible from manifest parsing alone.

WebKit's [native UI delegate implementation](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/Cocoa/UIDelegate.mm) checks the returned view's opener frame or related view against the supplied configuration. The [extension-page configuration](https://developer.apple.com/documentation/webkit/wkwebextensioncontext/webviewconfiguration) is the public entry point for privileged extension pages. These contracts rule out a casual replacement with an unrelated view; they do not justify a claim of complete popup support.
